# 排雷式交付规范（Mine-Clear Delivery · MCD）

> **受控原文（canonical）**：本规范由 `workloom-im` 维护，经 base-sync 分发到注册的订阅仓只读副本（隔离副本 `workloom-growthtest` / `workloom-growthmatrix` 不接收，见 `docs/DEVELOPMENT-PROTOCOL.md` §11）。
> **版本**：`mcd/v1.0`（2026-09-29）。
> **执行证据契约**：2026-10-02 加固；`workloom.evidence-run/v1`、`workloom.acceptance-item/v1`、`workloom.evidence-index/v1`，字段见 `docs/mine-clear/evidence.schema.json`。
> **融合来源**：①《AI-Coding 项目交付排雷方法论 V3.0》（七阶段模型 + 十条纪律 + 七套指令模板）；②本仓 `docs/REAL-DEVICE-ACCEPTANCE-SPEC.md`（RDAS v3.1 真机深度验收，276 项）；③`docs/DEVELOPMENT-PROTOCOL.md`（任务卡 / 锁 / 门禁 / 合并）；④`AI-AUTONOMOUS-OPERATIONS.md`（自治档位、信任工程、无回执不算完成）。
> **一句话定位**：把"看起来做完了"变成"敢让客户签字"——先系统性挖出挡交付的问题，再做有断言兜底的修复，最后交给独立验收背书。
> **规范正文与执行器**：本文件 + `docs/mine-clear/ledger.schema.json`（台账 schema）+ `docs/mine-clear/report-template.md`（报告模板）+ `docs/mine-clear/prompt-pack.md`(七套投喂模板) + `scripts/delivery/mine-clear.mjs`（执行器）。

## 0. 调用声明（关键词 / 指令 / 意图 → 动作）

本节是**面向所有 Agent 的触发契约**（人读速览与机器触发的唯一入口）。命中任一关键词后，先读本规范，再用执行器登记台账；**未命中不得主动打断常规任务**。

| 用户说的话（任一命中） | 采用档位 | 动作 |
|---|---|---|
| 排雷 / 排雷式交付 / 系统性排查 / 全面排查 / 交付前排查 / 交付体检 / 挖问题 / 找问题清单 / 深挖 / MCD / mine-clear | **A · 全景档（M0→M6）** | 按 §5 全阶段执行；产出 `outputs/mine-clear/<任务号>/{baseline.json,ledger.json,evidence/,report.md}`，M6 交 RDAS |
| 只看代码有什么坑 / 静态排雷 / 代码审计 / 走查目标链路 | **B1 · 静态域（M1）** | 目标链路逐行走查 + 坏味道 grep + 不变量绕过路径 |
| 压测 / 并发 / 异常注入 / 边界 / 状态机 / 跑一遍看会不会炸 | **B2 · 动态域（M2）** | 五维用例矩阵 + 取证三件套 + 可复跑脚本 |
| 联动 / 投影 / 数据对不上 / 各界面看不到 / 改了 A 破了 B | **B3 · 联动域（M3）** | 联动图 + 真机制造状态变更后逐面取证 |
| 装不上 / 客户机能不能跑 / 安全边界 / 越权 / 性能 / 日志有没有 | **B4 · 交付面（M4）** | 构建门禁 + 安装自包含 + 安全 + 性能 + 可观测 |
| 修复排期 / 批量修复 / 回归 / 修完怎么验 / 三次修不好 | **C · 修复档（M5）** | 四批排序 + 一卡一会话 + 断言转绿 + 回执 |
| 独立验收 / 第三方验收 / 验收报告 / 上线前验收 | **D · 验收档（M6）** | **不在本规范实现**：交接给 RDAS v3.1（`docs/REAL-DEVICE-ACCEPTANCE-SPEC.md`），见 §9 |
| 单点小改 / 纯问答 / 只要一段代码 / 明确说"快速看一下" | 不触发 | 按常规任务执行，不建台账 |

调用器（本地与各仓一致）：


## 1. 根本认知：问题分四层，每层要用不同的手段挖

AI 主导开发的项目，失败不是随机的。问题按"可见性"分四层，**静态审查只能挖到第一层**：

| 层 | 问题类型 | 挖法 | 典型实例（WorkLoom 语境的形状） |
|---|---|---|---|
| L1 代码层 | 逻辑错误、边界缺失、状态机断点 | 静态审计（M1） | 授权只按数组序号映射，内容从不比对；守卫读的字段在生产路径上根本没人写 |
| L2 装配层 | 配置缺失、接口错接、环境依赖 | 真机运行（M0/M2） | 客户端打包从未注入关键环境变量；`.env` 缺项导致启动即降级 |
| L3 运行层 | 并发竞争、异常路径、时序 | 动态压测（M2） | 12 路并发写库 10 个 500；重复提交把账本写出重复事件 |
| L4 语义层 | 假交付、联动断裂、文不对题 | 目标导向端到端验证（M3） | 用户要改价格，系统交付了一份经营日报且显示"已完成" |

补充一个**互补视角**（用在用例设计口径上，不替代四层）：业务错误（能跑但结果不对）／配置错误（依赖了不存在的配置项）／环境错误（本机能跑、出厂默认配置报错）。前者管"用什么手段挖"，后者管"在哪里炸"。

### 1.1 修复也分三种"假"（独立验收存在的理由）

| 假修复形态 | WorkLoom 语境的形状 |
|---|---|
| 只修主路径，分支路径没修 | 高危守卫只覆盖"任务挂起"这一条快照路径，其他来源的高危审批照批 |
| 修复方案之间互相打架 | 输出截断修复把知识库接入修复的效果吃掉 |
| 改了 A 破了 B（联动地雷） | 规划器缺参步骤绕过强制审查标记 → 假熔断 |

修复者知道"自己改了哪里"，会不自觉地只验证改过的地方。因此 **M6 必须由没参与修复的角色/会话执行**（协议 §1「合并在机器」不替代这一点）。

### 1.2 三个基线时刻（最容易白干的浪费）

AI 协作链路里最贵的浪费不是修错，而是**在旧代码上修**：审计在 commit A 出的台账，修复却落在云端已前进后的旧快照上。

| 基线 | 规则 | 硬动作 |
|---|---|---|
| **审计基线** | 审计前 `git fetch`，记录 commit；每张问题卡标注该基线（行号只对该基线有效） | `mine-clear.mjs init` 写入 `baseline.audit` |
| **修复基线** | **每张修复卡动手前**重新 fetch 对比；云端已前进 → 先 rebase 到最新，并**确认问题在新代码上仍然存在**再动手 | `mine-clear.mjs verify-baseline` 输出 stale 卡清单 |
| **验收基线** | 验收前拉取包含全部修复提交的版本，用 `git merge-base --is-ancestor <修复commit> <验收commit>` 核验后代关系 | 写入 `baseline.acceptance`，M6 第一道闸口 |

并行协作补充：多张卡可能改同一文件（核心文件常被多张卡命中）——排期时显式标注**冲突面**，同文件的卡串行或合并；每张卡从最新主干切分支、完成即合回，不留长命分支；每轮合入后刷新未修卡的行号引用。

### 1.3 上下文即质量（会话管理是工程问题）

- **一卡一会话**：每张修复卡/验收卡开新会话执行，任务间清理上下文；任务卡必须自包含（不看聊天历史也能落地）；
- **死循环退出**：同一个问题修了三次还不行——停止推进，开新会话、收窄问题、带上更好的证据（完整报错原文、数据库现场、最小复现）重来；
- **版本幻觉对策**：agent 坚称某个 API/方法"存在"时不要争论，让它去查当前版本的依赖文档或源码；
- **过度依赖滑坡**：人前三次仔细、之后开始扫一眼——所以纪律要**编码进确定性门禁**（测试 / hook / CI），不能只写在文档里靠自觉；
- **上下文读数只认实测**：需要缩范围时必须给出系统读数与理由，不得用"感觉快满了"降级交付。

### 1.4 验证信号前置：先给"完成"一个可运行的定义

每张问题卡/修复卡在**动手之前**就定义可执行的验收断言（输入 → 预期 → 实际）：

- **样例断言**：具体输入 → 具体预期，兜底；
- **属性断言**：不变量在任意输入下成立（如"任何参数缺失的写动作都不得跳过人工审查"），覆盖样例漏掉的边缘情形；
- **证据优先于声明**：完成必须出示断言输出原文，不接受"应该修好了"。
- **记录由真实执行产生**：断言给出 `exec.file/exec.args`；提交被测源码后运行 `run-assertions`，捕获实际退出码、信号、时间、角色与文件散列。`fail/not-run` 或裸路径不得进入 `verified`。

## 2. 七阶段模型（M0–M6）

```
M0 环境就绪 ─▶ M1 静态排雷 ─▶ M2 动态排雷 ─▶ M3 联动排雷 ─▶ M4 交付面验证 ─▶ M5 修复与回归 ─▶ M6 独立验收
（跑起来）      （读出来）      （炸出来）      （辐射出来）      （验出来）        （修一批绿一批）    （RDAS 签字背书）
      └──────── 发掘：问题卡（实证 + 根因 + 修法 + 验收断言）+ 可复跑证据脚本 ────────┘              │
   ▲ 三基线显式对齐 ｜ 一卡一会话 ｜ 验证信号前置 ▲                                                   │
      └────────────── 未闭环 / 新发现 → 回 M5 快速修复 → M6 复验（只跑未闭环断言） ◀────────────────┘
```

> 阶段编号刻意用 `M0–M6`，与 RDAS 的 `P0–P3`（生产实测域）区分：**M 域负责"挖与修"，P 域负责"生产实测"，两者在 M6 汇合**。

### M0 环境就绪：先建"最小真机"

- `git fetch` 后检出云端**最新**代码，记录基线 commit；
- 真实数据库 + 真实服务端 + 真实鉴权 + 种子数据；外部依赖用 mock；**一律出厂默认配置**（那是客户拿到手的真实形态）；用项目自带 bootstrap/seed，跑不通本身就是第一批问题；
- 冒烟：健康检查 + 一条核心业务链路；
- **提取系统不变量**：从 `AGENTS.md` §4（十二条）与 `WORKLOOM_PRODUCT_CONTEXT.md` §8 摘出本次要守的不变量清单，写进台账 `invariants[]`——它是后续所有断言设计的骨架；
- 环境常驻不拆，后续每轮实测、回归、验收都在它（或它的干净复制品）上进行。
- **产出**：`baseline.json`（基线 commit / 组件状态 / 冒烟结果）+ 不变量清单 + 安装层问题卡 + 可复跑起停命令。

### M1 静态排雷：以"用户目标链路"为轴读代码

- 选 1–3 条用户目标链路逐行走查（**不按目录泛读**），每个问题精确到 `文件:行号@commit` + 触发路径；
- 逐条对照不变量，找出**现实中可绕过**每条不变量的路径；
- 全局 grep AI 高频坏味道：`max(id)+1` 号源 / 无锁计数、`JSON.parse` 无 catch、HTTP 调用无超时无 signal、硬编码限制、他行业词进通用路径、进程内单例关键状态、`catch` 静默吞错、TODO/演示注释指向的代码、**守卫空转**（先 grep 消费点，再 grep 生产写入点核对）；
- 有同类历史故障报告（`docs/AUDIT.md`、错题本、事故卡）就逐条比对移植——同源代码库的故障高度遗传；
- **正负对照**：同时列出"审计确认无问题的关键环节"。

### M2 动态排雷：五维用例矩阵，让系统在异常下开口

- 五维：主链路闭环 / 并发竞争 / 异常注入 / 边界值 / 状态机遍历（特别找"没有出口的状态"）；
- 三类错误各补一组：业务错误、配置错误（缺配置时的行为）、环境错误（出厂默认 vs 全配）；
- 取证三件套：**API 响应原文 + 数据库特权直查 + 服务端日志**（日志缺失本身上账，判为可观测性缺陷）；
- 静态卡中能在运行中复现的，复现并升级为"运行实锤"；
- **每个用例留下可复跑脚本**（幂等或自带清理），它是修复回归与最终验收的引信。

### M3 联动排雷：每个状态变更问"辐射到哪些面"

- 画联动图（数据源 → 投影 → UI 映射），标出代码位置；
- 逐面核查断点模式：投影只读部分数据源、生产-消费字段名/枚举不匹配、优先级永久压制、依赖客户端见证才生效（换入口/刷新/自动任务还生效吗）、归属错配、新实体不可见；
- 所有问答入口（搜索 / 助手 / 报表）验证回答的数据源覆盖应覆盖的域；
- **必须端到端制造真实变更后到每个面取证**，不许只看代码推断；健康面也要列出（防修复误伤）。

### M4 交付面验证：把自己当验收方

- 构建与门禁：生产构建、类型检查、既有测试套件全绿（记录耗时与警告）；
- 安装自包含与密钥随机化、升级保留配置；
- 安全边界：绑定地址与 CORS、越权（租户 B 凭据读租户 A 数据应返回空而非泄露存在性）、注入式输入打每个文本入口、批量高危守卫；
- 真实数据量性能：打 3 个最重接口；
- 可观测：制造 5xx，检查日志是否有记录；
- **通过项与失败项同等上账**。

### M5 修复与回归：排期即学问，动手先对齐基线

- **基线检查**：每卡动手前 fetch → rebase → 确认问题仍存在 → 再改；
- **一卡一会话**：自包含任务卡 + 新会话执行；同文件冲突面显式标注；
- **验证信号前置**：先写/先指定可运行的验收断言（能写失败测试就先写测试），修到断言转绿为止；
- **四批排序**：`第 0 批 止血` → `第 1 批 地基` → `第 2 批 正确性` → `第 3 批 体验`；每批结束系统必须正向收敛；
- 每卡必做**联动地雷推演**：此改动改变谁的行为 / 谁依赖被改的文案·字段·顺序；
- 每批后跑：门禁命令 + 排雷期全部证据脚本；合入后刷新未修卡行号引用；
- 修复卡格式：实证 → 根因（`文件:行号@commit`）→ 修法（代码级）→ 验收断言 → 联动风险 → 回滚方式；
- 三次修不好 → 按 §1.3 换会话带更好的证据重来。

### M6 独立验收：交接给 RDAS v3.1

本规范不重复实现验收引擎。M6 = 用 `mine-clear.mjs handoff` 生成交接单，再由 RDAS v3.1 执行（见 §9）。**灵魂三问**：原来的问题还在吗？修复引入新问题了吗？客户的真实旅程走得通吗？前置闸口：验收基线是修复基线的后代吗？

## 3. 产物与落盘约定

```
outputs/mine-clear/<任务号>/
  baseline.json        # 审计基线（commit/branch/工作树态/冒烟结果/不变量清单）
  ledger.json          # 问题卡 + 修复卡 + 断言 + 证据（schema：docs/mine-clear/ledger.schema.json）
  evidence/            # 断言输出、日志摘录、响应原文、截图、脚本运行记录
  runs/                # 实际运行 JSON：完整 commit / argv / exit / 角色 / 起止时刻 / 输出引用
  approvals/           # 独立批准来源 JSON（仅需要豁免时）
  evidence-index.json  # 运行记录与真实输出文件索引
  report.md            # 排雷报告 / 修复报告（模板：docs/mine-clear/report-template.md）
  handoff.json         # M6 交接单（RDAS 验收输入）
```

**证据分级**（与 RDAS 一致，报告逐条标注）：

- **A**＝代码精读得出；真机实测另注明环境、步骤及原始证据；
- **B**＝全量机检 / 元数据解析得出；
- **C**＝抽样得出；
- **D**＝推断 / 未验证。

B/C/D 级结论不得使用"确认""全部""通读"等 A 级措辞。

**报告四段硬性内容**（缺一视为该轮排雷未完成，与 RDAS 报告同规矩）：覆盖率声明 / 证据分级 / 收尾报告 / 自检表。

## 4. 与 CNB 开发协议的绑定（不做例外）

排雷不是"另一套流程"，它跑在既有协议之上：

| 协议条款 | 在排雷里的落地 |
|---|---|
| §1 一任务一分支一 PR；任务号进提交信息；先声明后落笔 | 每轮排雷/修复开一张任务卡（`node scripts/tools/task.mjs new`），分支 `task/T-YYYY-MMDD-XXXX`，提交信息带任务号 |
| §2 四问 | 建卡时答全，含"会不会动租户边界/围栏/审批/事件/回执"；答不清即 `risk/review` |
| §3 目录围栏 | 修复若落在 `sync/**`、`protocol/**`、`AGENTS.md`、`.cnb.yml`、迁移等治理路径 → `risk/review` 人审放行 |
| §4 锁 | 排期时按模块互斥与路径重叠检测排冲突面，同文件卡串行或合并 |
| §5 提交规范 | `fix(<layer>): <摘要> [T-YYYY-MMDD-XXXX]` |
| §6 交接与恢复 | 上下文切换/跨终端接手前写交接单；排雷台账 + `ledger.json` 即跨会话自包含任务卡 |

## 5. 十条纪律（可执行条款，不是口号）

1. **无证据不上账**：每个问题必须有实证（`文件:行号@commit` / 日志 / 数据库记录 / 响应原文）；证据优先于"已修复"的声明。
2. **正负对照**：每轮既报问题也报实测通过项。
3. **脚本即证据**：每个动态发现配可复跑脚本；修复与验收就是"脚本红变绿"。
4. **目标对照**：判定标准是"用户要的东西交付得对不对"，不是"系统报没报错"。
5. **修缮不修穷**：只追"挡交付"的问题；每个问题必须回答"它挡得住交付吗"。
6. **基线显式对齐**：任何阶段开始前先确认手里的代码是不是云端最新；修在旧代码上是最贵的无用功。
7. **修复者不自验**：干活的不给自己打分；验收与修复角色分离（独立环境、独立断言、独立结论）。
8. **验收报告敢泼冷水**：背书的价值来自客观；"有条件通过 + 明确未闭环清单"比"一切正常"更能帮客户做决策。
9. **验证信号前置**：每个任务动手前就有可运行的通过/失败信号；纪律编码进确定性门禁（测试 / hook / CI），不靠模型自觉、不靠人一直仔细。
10. **上下文即质量**：一卡一会话；三次修不好就换会话带更好证据重来；agent 坚称某 API 存在时让它查当前版本文档而非争论。

## 6. 执行器与台账

`scripts/delivery/mine-clear.mjs` 是**编排与门禁**，不是"自动修 bug"的魔法：

| 子命令 | 作用 | 关键退出码 |
|---|---|---|
| `init` | 记录审计基线 + 生成 `ledger.json` 骨架（含不变量占位） | 0 / 2 参数错误 |
| `card-template` | 打印问题卡或修复卡模板（可直接填好 `add`） | 0 |
| `add` | 校验并回读一张卡的真实提交 blob/发现文件；已闭环卡还须回读运行证据 | 1 校验失败 |
| `run-assertions` | 显式执行该卡全部 argv 断言，捕获实际结果；`--actor` + `--role repair/acceptance` | 0 实际通过 / 1 失败或超时 / 2 参数或环境错误 |
| `gate` | 回读三基线、断言输出与独立角色；P0/P1 非 `verified` 即红 | 1 门禁未过 |
| `status` | 按级别 / 批次 / 状态统计，列出未闭环清单 | 0 |
| `plan` | 生成四批修复计划 + 冲突面（同文件卡）分组 | 0 |
| `verify-baseline` | 每卡基线 vs 当前 Git 历史：`current / needs-relocate / diverged / unknown`；显式记录抓取结果 | 1 存在 stale 卡 / 2 抓取失败或环境错误 |
| `handoff` | 生成 RDAS 验收交接单（含每条未闭环断言的复验命令） | 1 存在无回归路径的未闭环卡 |

`gate` 与 `handoff` 是**机器可判定的硬闸**：通过声明必须能回读到同一提交、同一卡、同一断言和独立执行角色的实际成功记录。

### 6.1 真实执行与回读规则

1. `baseline.audit/repair/acceptance.commit` 在门禁时必须是本仓存在的完整 40 位 SHA。实际核验 `audit` 是 `repair` 的祖先、`repair` 是 `acceptance` 的祖先、`acceptance` 等于当前 HEAD；tracked 改动及未被 gitignore 排除的 untracked 文件均使被测源码未验证。M0 的 repair/acceptance 可保留 null，但不能凭该骨架通过 gate/handoff。
2. 发现类代码证据使用 `file:line@commit` 与提交 blob 的 `sha256`；根因文件、行号和提交也要真实存在。非代码证据绑定 `{path, sha256, commit}`，相对台账目录回读。目录、空文件、symlink、越界路径和散列不符不能替代证据。
3. `assertion.exec` 是 `{file,args}`，执行器不经过 shell。必须为有通过/失败信号的实际断言。`run-assertions --role repair` 通过只进入 `fixed`；独立 `--role acceptance` 通过才进入 `verified`。通过前置条件后、首个实际执行前先落盘 `unfixed/not-run`、清旧验收基线与验证声明，保留 `last_assertion_attempt`；证据索引发布出错/中断也不得保留旧绿。失败、超时、找不到可执行文件均记录实际原因并保持 `unfixed`。
4. 每条运行记录含 `command/exec/actor/role/subject/commit/started_at/finished_at/exit_code/signal/validation/result/outputs`。`pass` 必须对应实际 exit 0、无失败信号、断言观测通过和干净提交；时间不能早于绑定提交、逆序或指向未来。MCD 的 subject 必须匹配 `{card_id,assertion_index}`，`verification_evidence` 必须引用本卡独立验收运行。Node `--test` 清理 `NODE_TEST_CONTEXT` 并注入受控 TestsStream observer；`requested_exec` 绑定声明 argv、`exec` 绑定实际 argv，`node_observer` 绑定观测器和逐文件机器摘要。零匹配、全跳过、空文件或缺逐文件摘要不能通过；原始 exit 0 不会被伪改成 1，而是记录 `validation.ok=false/result=fail`。人工报告文本及外层文件加载的 passed 不算实际断言。
5. `P0/P1` 问题只有独立 `verified` 才闭环。`fixed/covered/wontfix` 不能绕过；发现被其他提交覆盖时仍要在当前验收基线复跑。`P2` 未闭环项可以交接，但每项必须给出明确 `regression.command`。
6. 同 actor 豁免须有独立 `approved_by/approved_at/reason/source`。source 回读为 `workloom.evidence-approval/v1`，批准的 commit、卡号、范围 `role-separation`、原因和批准者必须与声明一致；批准者不能是修复/验收者。只有 reason 或不可回读来源不能放行。原始批准事件可用 `source_uri` 关联，供独立验收者核对身份。actor 是调用方传入字符串，绑定 JSON 不是平台签名身份认证；可信协调者必须分配真实未参与修复的会话并保留来源，本地检查不证明调用者身份。
7. `init` 抓取失败时记录 `fetch_status=failed`、`fetched_at=null`，明确只取得本地基线；`verify-baseline` 抓取失败不能放行。显式 `--no-fetch` 仅核验本地 Git 历史，不声明云端最新。

```bash
node scripts/delivery/mine-clear.mjs run-assertions --ledger <台账> --card MC-001 --actor <修复会话> --role repair
node scripts/delivery/mine-clear.mjs run-assertions --ledger <台账> --card MC-001 --actor <独立验收会话> --role acceptance
node scripts/delivery/mine-clear.mjs gate --ledger <台账>
```

RDAS 共享相同证据契约：固定 276 个唯一 ID、检查单散列与完整提交不可裁剪；每项需要同 ID 的原始 `expected/actual/pass`、实际运行和真实输出引用，不能从聚合成功扩展通过。批准的不适用须用范围 `not-applicable` 的独立来源，仍保留在固定分母中。报告再次复核每项与阶段输入，P 域另回读独立 receipt/transcript、同线程原始事件与状态断言、真实媒体产物及 reserve→commit 配额账本，实际 calls/tokens、未计量用量与冻结原因必须一致。缺失/不一致/实际计量未知为 `unverified`（退出 2），实际失败为 `fail`（退出 1）；仅完整 pass 退出 0。`reportGenerated=true` 与 `acceptancePassed=true` 分别表达生成报告和验收通过。

## 7. M6 交接：与 RDAS v3.1 的接口

交接单（`handoff.json`）字段：

```json
{
  "schema": "workloom.mine-clear/handoff@1",
  "task_id": "T-YYYY-MMDD-XXXX",
  "repo": "workloom-im",
  "audit_baseline": "<commit>",
  "repair_baseline": "<commit>",
  "acceptance_baseline": "<commit>",
  "invariants": [{"id": "INV-1", "text": "...", "source": "AGENTS.md#4.1"}],
  "closed_problems": [{"id": "MC-001", "assertions": [{"command": "node --test ...", "exec": {"file": "node", "args": ["--test", "..."]}, "last_result": "pass", "evidence": {"path": "evidence/....txt", "sha256": "<64hex>", "commit": "<40hex>"}, "run": {"path": "runs/....json", "sha256": "<64hex>", "commit": "<40hex>"}}]}],
  "open_problems": [{"id": "MC-007", "evidence": "...", "regression": "node ...", "fix_plan": "..."}],
  "acceptance_commands": [
    "pnpm acceptance:profile:check",
    "node scripts/acceptance/fleet-run.mjs --repo workloom-im --env client-runtime --live-only"
  ],
  "environment_claim": "local-preview | client-runtime | deployed",
  "notes": "未闭环项均为小改动；修复后只跑未闭环断言复验"
}
```

**验收三档结论**（RDAS 报告口径）：完全通过 / 有条件通过（未闭环项均为小改动且回归路径明确）/ 不通过。有条件通过时，每个未闭环项必须写明"修复后跑哪个脚本哪条断言回归"。

**环境档位是硬约束**：本机预览（`LLM_PROVIDER=mock`）只能写"本机预览结构验收"；只有 `client-runtime` / `deployed` + RDAS P 域真实任务全绿，才能写"生产实测通过"（RDAS v3.1 §0）。

## 8. 边界与诚实声明

- 本规范保证"**影响交付目标**的问题被系统性暴露并被独立验证修复"，不保证找出所有理论缺陷；
- L4 语义层问题的挖掘质量取决于**目标链路定义得准不准**——定义错了后面全错；
- 基线纪律解决"修在旧代码上"，但不替代代码评审：并行合入的语义冲突（两张卡都"对"但合在一起逻辑矛盾）仍需评审或真机回归兜底；
- 独立验收的独立性取决于执行者纪律：用修复者的环境、只看修复者的验证记录，验收就退化成走形式；
- "AI 修 AI"闭环可以提效，但**签字前保留一次人工抽查**（核心旅程一遍 + 未闭环项的回归脚本一遍）；
- 过度依赖是慢变量：流程跑得越顺，人越容易放弃抽查——把人工抽查写成日历事件；
- 隔离副本（growthtest / growthmatrix）不在本规范的默认覆盖范围内。
