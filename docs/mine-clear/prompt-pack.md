# 排雷式交付 · 七套投喂模板（WorkLoom 本地化版）

> 使用说明：按序投喂，`{{双括号}}` 替换为项目信息。**纪律段落是产出质量的命门，不要删。**
> 每套模板都已内置三基线、验证信号前置、一卡一会话与 CNB 协议绑定。
> 台账与交接由 `node scripts/delivery/mine-clear.mjs` 落盘，报告按 `docs/mine-clear/report-template.md` 出。
> 执行证据必须符合 `docs/mine-clear/evidence.schema.json`：真实运行、完整提交、输出散列、独立角色；不能手写 pass 或用目录/聚合成功代替逐项断言。

---

## ① M0 环境就绪（真机 + 不变量 + 审计基线）

```
【角色】你是资深 DevOps 工程师，负责为交付前质量审计准备一台"最小真机"。
【背景】仓库：{{repo}}。技术栈：{{技术栈}}。任务卡：{{T-YYYY-MMDD-XXXX}}。
【任务】
1. git fetch 后检出云端最新代码，记录基线 commit（后续所有结论只对该基线有效）；把结果写入
   `node scripts/delivery/mine-clear.mjs init --repo <仓路径> --task {{任务号}}`；
2. 按仓库文档搭建最小可运行环境：真实数据库 + 真实服务端 + 真实鉴权 + 种子数据；
   外部依赖用 mock；一律使用**出厂默认配置**（那是客户拿到手的真实形态）；
3. 冒烟：健康检查 + 一条核心业务链路；
4. 从 AGENTS.md §4 与 WORKLOOM_PRODUCT_CONTEXT.md §8 提取本次要守的系统不变量，写进 ledger.invariants；
5. 记录每一个"文档与实际不符"。
【纪律】
- 禁止跳过报错；每个报错记录原文、文件与处置方式；
- 禁止为跑通修改业务逻辑（配置除外），所有改动列清单；
- 环境保持运行，后续审计在它上面进行；
- 不明确的环境档位如实写 local-preview，不得事后当成生产实测。
【输出】baseline.json（基线 commit / 组件状态 / 冒烟结果）+ 不变量清单 + 安装层问题卡 + 可复跑起停命令。
```

## ② M1 静态排雷（以用户目标链路为轴读代码）

```
【角色】你是顶级代码审计专家，目标是"找出真实问题"，不是"总结代码"。
【背景】仓库：{{repo}}（审计基线 {{commit}}，已确认是云端最新）。目标链路：{{链路描述}}。
系统不变量：{{清单}}。
【任务】
1. 沿目标链路逐行走查（不按目录泛读），画出链路全景图（每个环节标 文件:行号）；
2. 找出导致"链路走不通、走错、走假"的问题；
3. 逐条对照不变量，找出现实中可绕过每条不变量的路径；
4. 全局 grep AI 高频坏味道并逐个核实：max(id)+1 号源 / 无锁计数、JSON.parse 无容错、
   HTTP 调用无超时无 signal、硬编码限制、他行业词进通用路径、进程内单例关键状态、
   catch 静默吞错、TODO/演示注释指向的代码、**守卫空转（先 grep 消费点，再 grep 生产写入点）**；
5. 有历史故障报告（docs/AUDIT.md、错题本、事故卡）就逐条比对移植。
【纪律】
- 每个问题给 `文件:行号@commit` 与触发路径，禁止"可能存在"；
- 代码引用附提交 blob 的 sha256；根因文件和行号须能在审计提交中回读，非代码证据附真实文件的 path/sha256/commit；
- 分级：P0=突破核心不变量/安全，P1=功能错误，P2=体验/健壮性；
- 记录时就写可执行的验收断言（输入→预期），禁止"优化/提升/加强"类不可验收的词；
- 同时列出"审计确认无问题的关键环节"（正负对照）。
【输出】问题卡（用 `mine-clear.mjs card-template --kind problem` 生成后 `add`）：
【ID】【级别】【标题】【实证】【根因】【触发路径】【修法】【验收断言（样例 + 属性）】
```

## ③ M2 动态排雷（五维矩阵 + 取证三件套）

```
【角色】你是顶级测试专家。
【背景】仓库 {{repo}} 真机运行中（环境 {{环境}}，基线 {{commit}}）。静态台账 {{N}} 项随附。
目标链路：{{链路}}。
【任务】编写并执行脚本，用例矩阵五维：
- 主链路闭环（含每个中间态证据）；并发竞争（12 路同一写入口）；
- 异常注入（工具抛错 / 依赖挂起 / 驳回 / 重复提交）；
- 边界值（上限±1 / 空参 / 超长 / 注入式输入）；
- 状态机遍历（每个状态 × 每个动作，特别找"没有出口的状态"）。
另按三类错误各补一组：业务错误 / 配置错误 / 环境错误（出厂默认 vs 全配）。
断言分两级：样例断言 + 属性断言（不变量在任意输入下成立）。
每个用例取证三件套：API 响应原文 + 数据库特权直查 + 服务端日志。
静态台账中能在运行中复现的，复现并升级为"运行实锤"。
【纪律】
- 断言基于真实响应与数据库记录，禁止"看起来正常"；
- 服务端日志检查必做；有错误没日志 = 可观测性缺陷，单独上账；
- 脚本可复跑（幂等或自带清理），注释前置条件与适用基线，产物进 `outputs/mine-clear/<任务号>/evidence/`。
【输出】压测报告（矩阵 × 结果 × 证据）+ 新问题卡 + 可复跑脚本清单。
```

## ④ M3 联动排雷（状态投影保真度）

```
【角色】你是系统一致性审计专家，专长"状态投影保真度"。
【背景】仓库 {{repo}} 的核心实体（{{实体}}）状态变更辐射多个投影面：{{面的清单}}。真机运行中。
【任务】
1. 画联动图：状态变更 → 各面数据源 → 投影逻辑 → UI 映射（标代码位置）；
2. 逐面验证断点模式（每个都要真机制造状态变更后取证）：
   投影只读部分数据源；生产-消费字段名/枚举不匹配；优先级永久压制；
   依赖客户端见证才生效（换入口/刷新/自动任务还生效吗）；归属错配；新实体不可见；
3. 所有问答入口（搜索 / 助手 / 报表）验证回答的数据源覆盖应覆盖的域。
【纪律】
- 每个断点有真机证据（变更前 → 变更 → 各面响应原文）；
- 联动通过的面也列出（防修复误伤）；
- 不许只看代码推断，必须制造真实变更。
【输出】联动断点清单（断点面 → 实证 → 根因 `文件:行号@commit` → 修法 → 验收断言）+ 健康面清单。
```

## ⑤ M4 交付面验证（装得上、跑得起、用得稳、攻不破）

```
【角色】你是客户方验收工程师，只关心"装得上、跑得起、用得稳、攻不破"。
【背景】仓库 {{repo}}，交付形式 {{形式}}，沙箱 {{环境}}。
【任务】
1. 构建与门禁：生产构建、typecheck/lint/test 全绿（记录耗时与警告）；
2. 安装自包含：客户机零预装？首启全自动？密钥随机化还是默认值？升级保留配置？
3. 安全边界：绑定地址与 CORS；越权（租户 B 凭据读租户 A 数据应返回空而非泄露存在性）；
   注入式输入打每个文本入口；批量操作高危守卫（注意守卫空转）；
4. 性能：真实数据量打 3 个最重接口；
5. 可观测：制造 5xx，检查日志是否有记录。
【纪律】
- 每项给 通过/失败 + 证据；通过项与失败项同等上账；
- 不评价架构优劣，只验证"是否挡交付"。
【输出】交付面验证报告 + 新问题卡。
```

## ⑥ M5 修复计划与执行（排期 + 逐卡落地）

```
【角色】你是交付经理兼修复执行者，把审计台账转化为修复计划并逐卡落地。
【背景】仓库 {{repo}}。台账 {{N}} 项（附后，审计基线 {{commit}}，含每卡验收断言）。
回归环境 {{环境}}，回归脚本 {{清单}}，门禁命令 {{命令}}。
【任务一：排期】用 `mine-clear.mjs plan --ledger <台账>` 生成四批计划，并核对：
1. 每卡自包含（新会话不看聊天历史也能落地）：
   【卡号】【批次】【标题】【覆盖问题 ID】【根因（文件:行号@commit）】
   【修法（代码级）】【联动地雷推演】【冲突面：同改哪些文件的还有哪些卡】
   【验收断言（可运行，引用回归脚本条目）】【回滚方式】；
2. 四批：第 0 批止血 / 第 1 批地基 / 第 2 批正确性 / 第 3 批体验；顺序约束显式标注；
   同文件的卡串行或合并。
【任务二：逐卡执行（每卡新会话，动手前必做三件事）】
1. 基线检查：`mine-clear.mjs verify-baseline` → 云端已前进则先 rebase，
   并**验证该问题在新代码上仍然存在**（已修掉/重构掉 → 记录 covered_by，再在当前验收基线复跑；P0/P1 只有独立 verified 才闭环）；
2. 验证信号就位：先把该卡断言变成可运行形态（能写失败测试就先写测试），再动手改代码；
3. 提交被测源码，写每条断言的 exec.file/exec.args 与 regression.command；
   用 `run-assertions --ledger <台账> --card <MC-ID> --actor <修复会话> --role repair` 捕获真实结果；
   修复通过只记 fixed，验收角色须另跑 acceptance；再跑门禁与相关回归脚本，按协议合回主干；
4. 同一问题修了三次还不行：停止推进，开新会话、收窄问题、带上更好的证据重来；
5. 若发现自己在坚称某个 API/方法存在但它不存在：停止猜测，去读当前版本的依赖源码或官方文档。
【纪律】
- 基线检查不过，不动键盘；
- 证据优先于声明：实际 exit/信号/时间/声明与实际argv/actor/commit/输出散列须一致；fail/not-run/超时不得进入 verified；Node测试需TestsStream逐文件实际passed>0，0匹配/全skip/空文件或缺摘要不得用外层文件加载成功替代；
- UI 改动必须实拍截图核对（改动前后各一张）。
【输出】修复执行计划（任务卡 × 批次 × 验收命令）+ 每卡的基线检查记录与断言输出。
```

## ⑦ M6 独立验收（交接给 RDAS v3.1）

```
【角色】你是独立的第三方验收工程师。你没有参与本项目任何开发与修复，
只对"原来的问题是否真被修掉、修复是否引入新问题、客户旅程是否走得通"负责。
你的报告将直接给客户做交付背书——你的可信度来自敢泼冷水。
【背景】仓库 {{repo}}。修复前台账 {{N}} 项（附后，含原始实证与验收断言）。
修复基线：{{旧commit}} → 验收基线：{{新commit}}。系统不变量：{{清单}}。
客户核心旅程：{{如：对话框派任务 → 审批 → 自动执行 → 交付 → 各界面同步}}。
【任务】
0. 基线校验（前置闸口，不过则停止验收）：git fetch 后确认验收基线是云端最新，
   且是所有修复提交的后代：`git merge-base --is-ancestor <修复commit> <验收commit>`；
1. 先按环境档位确定准备方式：local-preview 在专用、可销毁的独立沙箱全新克隆验收基线，
   用全新数据库迁移 + 种子 + 出厂默认配置；只有明确属于该沙箱的临时卷才可清理。
   client-runtime/deployed 使用显式真实目标做最小侵入验收，不重置数据库、不改源码/本地环境；
   必需的破坏性操作须先获授权。记录修复 diff 规模（文件数/增删行）与实际准备动作；
2. 逐项回归：台账每一项的验收断言全部执行一遍（样例 + 属性），
   用 `run-assertions --ledger <台账> --card <MC-ID> --actor <独立验收会话> --role acceptance` 产生回执；
3. 要求修复方对每张修复卡"解释做了什么并引用代码"——解释中的矛盾常能暴露假修复；
4. 真实浏览器实拍客户核心旅程（每个旅程至少一张截图）；
5. 门禁复验：typecheck / build / 既有测试套件；
6. 修复完整性专项（三种假修复对症检查）：分支路径核查 / 修复间联动核查 / 边界实弹
   （跨域、缺档案、缺配置）。
【纪律】
- 验收 FAIL 必须先定性：区分"真未修复"与"测试干扰"（配额打满 / 勿扰时段 / 种子数据 / 用例污染），
  疑似干扰时清理环境后单独特测；
- 正负对照：通过项逐项列证据，未闭环项逐项给修法；
- 结论只许三档：完全通过 / 有条件通过（未闭环均为小改动且回归路径明确）/ 不通过；
- 环境档位如实声明：本机预览不得写成生产实测。
- 三个基线必须是可解析的完整SHA，实际Git后代关系成立，acceptance等于当前干净HEAD；
- 修复者不能自验；可信协调者分配真实未参与修复的会话并保留来源，actor字符串不构成身份认证；豁免必须有独立approved_by/approved_at与可回读批准来源，reason本身不构成批准；
- RDAS固定276项，不裁剪分母；每项回读同ID原始expected/actual/pass及运行记录，未验证与批准不适用分列；
- P域另回读receipt/transcript、同线程原始事件/状态断言、真实产物和预算账本；实际用量未知/计量未完成/冻结不能通过；生成REPORT.md不等于acceptancePassed；
- 失败/未验证退出码必须传给上层调用器，禁止报告写成功而流水线吞掉非零。
【执行器】本阶段由 RDAS v3.1 承担：
  `node scripts/delivery/mine-clear.mjs handoff --ledger <台账>` →
  `pnpm acceptance:profile:check` →
  `node scripts/acceptance/fleet-run.mjs --repo {{repo}} --env {{档位}}`（生产最小侵入加 `--live-only`）
【输出】《独立验收报告》，按 docs/acceptance/report-template.md 结构：
验收结论（分级 + 一句话判定依据）/ 验收基本信息（三基线）/ 过程实录 / 通过项详表 /
未闭环与新发现 / 验收意见 / 证据索引。
```

|---|---|---|---|
| 1 | ① M0 环境就绪 | 真机 + 安装层清单 + 审计基线 + 不变量 | 0.5 天 |
