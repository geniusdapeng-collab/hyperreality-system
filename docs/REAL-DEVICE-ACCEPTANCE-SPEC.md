# 真机验收规范（Real-Device Acceptance Spec · RDAS）

> 适用：`sync/child-repos.json` 里的全部 WorkLoom 仓（含实验车道 fox / growth），以及其他声明 `workloom.product/*` 的行业实例。
> 事实源：本文件（规范正文）+ `docs/acceptance/checklist.v1.json`（机器可读检查单）+ `docs/acceptance/report-template.md`（报告模板）+ `scripts/acceptance/**`（执行器）。
> 演变：规范本体在基座维护，经 base-sync 分发到各仓只读副本；行业专属的“人员/旅程/阈值”写在**本仓** `acceptance/profile.json`，不回流基座（见 §13）。
> 版本：`rdas/v1`（2026-09-19 首次发布，来源：WorkLoom-growth 真机验收实战沉淀）。

## 0. 一页速览

| 问题 | 本规范的回答 |
|---|---|
| 验收和跑测试有什么区别？ | 测试回答“代码是否符合断言”，验收回答“**真实的人在真实入口上，能不能完成任务并拿到价值**”。二者都要，且验收必须用真机（真浏览器/真服务/真数据库），不接受“单测通过”代替。 |
| 验收的判定单位是什么？ | 不是“功能点存在”，而是**可度量的任务**（角色 × 旅程 × 维度），每条任务都要有 前置条件 / 步骤 / 预期 / 实测 / 证据。 |
| 证据怎么算数？ | 四类证据（运行时数字、页面/截图、数据库/账本、可复跑命令）互相独立；证据分级 A/B/C/D（§5），B/C/D 不得写成“确认/全部”。 |
| 什么情况必须拦住发布？ | §6 的发布红线：治理（围栏/审批/账本/回执）被绕过、关键任务不可完成、演示与真实混淆、秘密入文件、无回执宣告完成。 |
| 发现的问题怎么收口？ | §7 缺陷分级 + 修复 + 回归 + 账本留痕；每轮验收沉淀“陷阱清单”（§10），跨仓复用。 |
| 规范怎么落到 10 个仓？ | §13 落地：基座维护规范与执行器 → base-sync 分发 → 每仓 `acceptance/profile.json` 声明本仓人员/旅程/阈值 → 每轮产出 `outputs/acceptance/**` 与报告。 |

## 1. 目的、范围与术语

### 1.1 目的

把“上线前找问题”从**个人经验**变成**可复跑、可复核、可累积的舰队级机制**：同一套口径可以逐个验收 10 个仓，且每轮的新发现会沉淀回检查单，下一轮自动覆盖。

### 1.2 适用范围

- 基座仓（workloom-im）：公共运行时、三端壳、平台机制；
- 平台仓（workroom-andromeda）：平台运营与账号域；
- 行业仓（hotel / hyperreality / ecommerce / consulting / trading / 获客）；
- 实验车道（fox / WorkLoom-growth）：允许形态差异，但**不豁免信任与治理口径**（只增不改、围栏、审批、账本、回执、秘密红线一律适用）。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 真机 | 真实浏览器（Playwright/Chromium 等）+ 真实服务进程 + 真实数据库（种子态），**不是** HTTP mock 或快照断言 |
| 组合编制 | 多行业包在同一工作区合装后的**权威岗位集合**（含同名遮蔽裁决），事实源是装配器运行结果 |
| 走查 | 以某个角色身份、按剧本完成一组任务，同时记录时间/点击/文本/截图 |
| 证据等级 | A/B/C/D（§5.2），描述结论的证明强度 |
| 红线 | 一票否决项：触发即整轮验收判失败（§6.2） |
| 陷阱清单 | 从真实缺陷中抽象出的“通用失败模式 + 检查手段”（§10） |

## 2. 为什么需要它：三类真实教训（来自 WorkLoom-growth 首轮真机验收）

1. **“测试全绿”掩盖了整条主链不可用**：`pnpm suite` 461/461 全绿的同时，发布门禁的编排链路被自家门禁拦死（CEO 节拍的 actor 未声明围栏绑定 → F2.10 拒绝写入），晨报/裁决/熔断整链不可用。
   → 教训：**门禁要跨层验收**；单层全绿不构成发布依据（本规范 §3 的 L6/L7 层就是为这类问题设的）。
2. **交互在“看起来对”的地方失效**：审批三手势在 DOM 里存在、在无障碍树里有名字，但 480×560 的助手浮层矩形盖在上面，鼠标点不动；而脚本只检查了“按钮存在”。
   → 教训：**“存在”不等于“可操作”**；关键动作必须真实点按并核对写回（§4.3 的“可操作三连”：可见、可点、有回执）。
3. **验收者自身会污染被验对象**：套件每跑一轮都会留下排队线程，几轮后把并发配额占满，导致下一轮的派单用例成片失败；测试夹具线程标题也出现在演示工作区。
   → 教训：**验收环境的卫生是验收的一部分**（§7.4 环境与夹具治理）。

## 3. 验收分层模型（L0–L8）

每一层都必须产出证据；低层通过不等于高层通过。**裁剪必须显式声明**（§6.4）。

| 层 | 名称 | 要看什么 | 典型手段 | 事实源 |
|---|---|---|---|---|
| L0 | 契约与清单层 | 岗位/技能/围栏/对象/阶段/管线声明是否自洽：字段完整、键唯一、引用存在、写读一致、来源归属 | 静态校验 + 组合编制对账（矩阵 A 层） | `bundles/*/bundle.json`、`presets/*.yml`、`skills/*/SKILL.md` |
| L1 | 装配与运行层 | 组合编制在同一工作区**真的在编**：状态 ready、围栏与声明一致、技能已安装、来源留痕 | 数据库对账（矩阵 B 层） | `agents` / `fence_rules` / `skill_installs` / `bundle_installs` |
| L2 | 数据与迁移层 | 迁移可重放、种子幂等、事件链自洽、只增不改、回滚路径存在 | `db:migrate` / `db:seed` / `db:verify-chain` | 事件账本 + 迁移脚本 |
| L3 | 页面与路由层 | 三端全部入口可达、无控制台错误、无横向溢出、空态/错误态有下一步 | 真机爬取（路由清单由本仓 profile 声明） | 页面 + 浏览器控制台 |
| L4 | 任务与交互层 | 关键任务**真实完成**：派活/审批/溯源/工单/对话，且写回可见 | 走查脚本（点击 + 写回断言） | 页面 + 账本回执 |
| L5 | 体验与可访问层 | 时间、理解成本、术语一致性、对比度、键盘/读屏可达、打扰预算 | 计时走查 + 机检（术语扫描、对比度抽样、打扰计数） | 页面 + 采样数据 |
| L6 | 治理与信任层 | 围栏瀑布、审批手势、账本只增、回执真实、dry-run、熔断、租户隔离、PII 脱敏 | 治理用例 + 对抗用例（越权/伪造/绕过） | 围栏引擎 + 审批 + 账本 |
| L7 | 恢复与可运维层 | 断点续跑、失败关闭、暂停/撤回、夜班窗口、限流与并发上限、备份/回滚 | 演练 + 故障注入（混沌原则） | 运行时 + 运维脚本 |
| L8 | 能力与效果层 | 岗位与技能在**专业场景**下能否交付合格结果（评分卡 + 红线一票否决） | 场景任务 + 双评（人/模型）+ 考试院 | 评分卡 + 考试院题库 |

> 层间关系：L0/L1 是“有没有”，L2/L3 是“跑不跑”，L4/L5 是“好不好用”，L6/L7 是“敢不敢交”，L8 是“值不值钱”。

## 4. 验收矩阵：角色 × 旅程 × 维度 × 任务

### 4.1 角色（每仓按业务映射，至少覆盖 5 类）

| 角色 | 关注点 | 体验红线 |
|---|---|---|
| 经营者/董事长（owner） | 结果与风险一眼看清 | 每日投入 ≤10 分钟；高风险必须人审；随时可撤回 |
| 经理（manager） | 今天要处理什么、谁在做、卡在哪 | 待办不丢；职责清楚；异常有指引 |
| 一线员工（staff） | 系统给的活怎么接、怎么交 | 说明完整；交接有回执；不背锅 |
| 伙伴/渠道（partner） | 我能看什么、不能碰什么 | 权限逐条可见；资金类不可碰 |
| 终端客户（guest） | 问得清、答得快、能联系到人 | 首响 ≤30s；不编造；转人工顺畅 |

### 4.2 旅程（横轴）

首启（0–10 分钟）→ 首日（Day-1）→ 首周（节拍）→ 日常治理（每天 10 分钟）→ 异常处理（差评/熔断/超限/断网）→ 月度复盘与续费。

### 4.3 维度与通过线（可度量；阈值写在本仓 profile）

| 维度 | 通过线（默认值，仓可上调不可下调） | 测量方法 |
|---|---|---|
| 首次价值 | T+20s 内看到“系统已做什么 + 需我拍板 ≤7 件”；首启仪式 1 次点击可跳过 | 计时走查 |
| 关键任务可操作性 | 100%：**可见 → 可点 → 有回执**（三者缺一即失败） | 真机点按 + 写回断言 |
| 效率 | 派活 ≤60s；单件审批 ≤30s；溯源 ≤2 次点击 | 计时/点击数 |
| 理解度 | 岗位/技能 30s 内读懂；术语 100% 中文（无裸动作码、裸 id、裸 ISO） | 5 秒测试 + 术语扫描 |
| 信任与透明 | 每个数字可溯源到事件/回执；高风险必经人审；熔断可见 | 溯源点击 + 围栏审计 |
| 掌控感 | 一键暂停/撤回可用；决策包 ≤7 件/日；授权变化可见 | 走查 + 计数 |
| 响应式与可访问 | 390px 无横向溢出；对比度达 WCAG 2.2 AA（正文 4.5:1、大字 3:1）；键盘可达 | 双视口 + 对比度抽样 + 键盘走查 |
| 人格与打扰 | 数字人称呼/语气一致；非 P0 不打扰（聚合汇报）；静置 20s 打扰 0 次 | 静置采样 + 对话评审 |
| 数据卫生 | 演示/测试数据不污染业务视图；mock 与真实明确区分 | 术语扫描 + 数据源标注核对 |

## 5. 证据规范

### 5.1 每轮验收必须产出（缺一即未完成）

1. `outputs/acceptance/matrix/`：员工/技能矩阵 JSON + CSV + 摘要（含失败清单与警告清单）；
2. `outputs/acceptance/ui/`：路由/页面探针 JSON + 关键截图；
3. `outputs/acceptance/experience/`：走查报告 JSON + Markdown + 截图；
4. `outputs/acceptance/regression/`：套件、门禁、验链、类型检查的原始日志摘要；
5. `outputs/acceptance/REPORT.md`：按 `docs/acceptance/report-template.md` 成文，含**覆盖率声明 / 证据分级 / 收尾报告 / 自检表**四段（硬性）。

### 5.2 证据分级（写结论时必须标注）

| 级 | 含义 | 允许的措辞 |
|---|---|---|
| A | 代码精读 + 真机实测（可复现） | 确认、已修复、通过 |
| B | 全量机检/脚本解析（覆盖率全但理解浅） | 机器判定为、全量扫描显示 |
| C | 抽样 | 抽样显示、疑似 |
| D | 推断/未验证 | 推测、未验证 |

### 5.3 防伪与“如实标注”

- mock / 模拟 / 演示态必须在数据与界面**双处**可辨认（`dataMode=simulated` 等）；
- 回执位必须区分三态：`无回执（未核实）`、`synced:false（已执行但无外部回执）`、`synced:true（真实回执）`——**不得用省略字段表达“未核实”**（否则下游无法区分“未核实”与“数据缺陷”）；
- 事件账本只增不改；验收产生的测试写入必须可识别（前缀/workspace/夹具标记），并在报告中披露；
- 截图/日志/JSON 必须与命令一一对应（报告里给复跑命令）。

## 6. 判定、红线与例外

### 6.1 通过判定

- **整轮通过**：所有层的检查项全绿，或未绿项全部落在 §6.4 的显式豁免清单里（含理由与截止日）。
- **条件通过**：仅一般级问题未修，且有工单、责任人与回归计划；报告必须写“条件通过”。
- **不通过**：任一红线触发，或关键任务可操作性 < 100%。

### 6.2 发布红线（一票否决）

1. 治理被绕过：围栏 block 动作被执行 / 高风险动作未进人审 / 账本可被改写；
2. 关键任务不可完成：派活、审批、溯源、客户触达任一角色链路断；
3. 演示与真实混淆：模拟数据未标注、mock 结果被当真实回执；
4. 秘密与客户数据：令牌/密码/私钥/客户原始数据进入代码、日志、文档或上下文；
5. 无回执宣告完成：外部动作没有真实回执却标记完成；
6. 发布门禁未全绿（各仓 `.cnb.yml` / `release:gate` 类命令）。

### 6.3 缺陷分级与时效

| 级别 | 定义 | 处置 |
|---|---|---|
| 阻断（P0） | 主线不可用、数据损坏、治理失效、泄密 | 立即停止验收，修复 + 回归后重跑受影响层 |
| 严重（P1） | 关键任务可操作性受损、关键数据不一致 | 本批次修复；不能当场修的必须给降级方案 |
| 一般（P2） | 体验/文案/一致性/性能小问题 | 记录 + 排期；不影响本轮结论 |
| 建议（P3） | 优化项 | 进积压 |

### 6.4 裁剪与豁免（必须显式）

裁剪只允许三种理由：环境不具备（如无真实模型）、风险为零（如纯文案）、成本收益不成比例（如全量 8K 抽样替代）。
任何裁剪都要写：**裁了什么 / 为什么 / 影响哪条结论 / 何时补**。禁止“默默不做”。

## 7. 执行 SOP（单仓一轮，建议 0.5–1 天）

```
① 筹备（T-1）
   读 AGENTS.md / AGENTS.repo.md / 本规范 / 本仓 acceptance/profile.json
   记下事实源状态：分支、HEAD、依赖锁定、数据源（真实/模拟）、外部凭据就绪情况
② 基线冻结
   记录被测版本（commit SHA）、种子数据版本、依赖版本；此后只允许一处一处改动
③ 起服务（真机）
   profile 里的 startup 命令（如 pnpm preview:all）；确认端口、工作区、演示身份
④ L0/L1 矩阵（机器）
   pnpm acceptance:matrix → 员工/技能/围栏矩阵（A/B 层）
⑤ L2/L3 真机爬取
   pnpm acceptance:ui → 全部路由 + 全部档案页/技能卡 + 控制台错误 + 溢出
⑥ L4/L5 走查
   pnpm acceptance:experience → 角色 × 旅程 × 任务（计时/点击/术语/对比度/打扰）
⑦ L6/L7 治理与恢复
   围栏 dry-run、审批三手势、熔断、越权对抗、断点续跑、并发上限、备份回滚
⑧ L8 能力抽检（有真实模型时）
   P0 岗位 + 关键技能场景评分卡；无真实模型则明确标“未验证”
⑨ 回归
   主套件 + 领域套件 + 验链 + 类型检查 + 发布门禁；全部留日志
⑩ 收口
   REPORT.md（含覆盖率声明/证据分级/收尾报告/自检表）+ 缺陷工单 + 经验回写 §10 陷阱清单
```

### 7.4 环境与夹具治理（本轮新增的硬要求）

- 验收/套件必须在**独立工作区或独立数据库**运行；若共用演示库，跑完必须排空夹具（并发位、临时线程、临时技能），并在报告披露残留；
- 并发上限、限流、配额等“保护自己的机制”本身也要验收：确认拒绝信息的可读性，并确认不会因历史夹具把自己锁死；
- 事件只增不改：清理只允许作用于**未进入账本**的夹具；
- 每轮开始前跑一次“环境体检”（端口/健康检查/演示身份/数据模式）。

## 8. 工具与配置契约

### 8.1 执行器（随基座分发）

| 命令 | 作用 | 产物 |
|---|---|---|
| `pnpm acceptance:matrix` | L0/L1：组合编制 × 技能 × 围栏矩阵（A/B 层） | `outputs/acceptance/matrix/*` |
| `pnpm acceptance:ui` | L3/L4：路由 + 档案页 + 技能卡 + 控制台 | `outputs/acceptance/ui/*` |

### 8.3 报告模板要点

`docs/acceptance/report-template.md` 固定四段硬性内容（覆盖率声明 / 收尾报告 / 自检表 + 证据分级说明），其余章节可裁剪但不得删除这四段。

## 9. 组织与职责（人 + AI）

| 角色 | 职责 |
|---|---|
| 验收执行者（AI/工程） | 按 SOP 跑完 L0–L7，产出证据，修 P0/P1，写报告与陷阱清单 |
| 产品所有者 | 裁决 §6.4 豁免、红线例外、以及“要不要为体验问题推迟发布” |
| 仓负责人 | 审核本仓 profile（角色/旅程/阈值是否反映真实业务）、审合并验收相关 PR |
| 舰队维护者 | 维护规范本体与执行器；每轮把新陷阱清单合并进检查单 |

纪律：**验收者不得既当运动员又当裁判**——修复由代码作者做，验收结论必须由“重跑同一脚本”得出，而不是口头确认。

## 10. 陷阱清单（真实缺陷抽象，持续累积）

> 用法：每轮验收前逐条自问；新缺陷修复后必须抽象成一条新陷阱（症状 → 根因 → 检查手段），写回本表并同步到 `checklist.v1.json`。

| # | 症状 | 根因 | 通用检查手段 |
|---|---|---|---|
| T-01 | 门禁/发布链路自己拦自己（新加的安全校验把自家系统组件判成违规） | 安全校验只看“声明”，而系统内置组件没有走声明路径 | 新增门禁后，跑一遍**全部内部写路径**（节拍/夜班/巡检/自动化），不只看业务动作 |
| T-02 | 按钮“存在、可访问、有名字”，但点不动 | 浮层/抽屉/空盒子的矩形区域吞掉指针事件 | “可操作三连”：可见 → 真实点按 → 写回断言；对固定定位浮层做遮挡扫描 |
| T-03 | 页面控制台报 hydration/嵌套错误，但功能看起来正常 | 语义化标签嵌套违规（按钮套按钮等） | 控制台零错误纳入路由验收；对展示态组件区分“可点/只读”渲染 |
| T-04 | 术语裸奔（英文 id / 动作码 / ISO 时间直接上屏） | 展示层兜底词典在“含技术记号”时整串回落 | 术语扫描（正则族）+ 每个展示函数配单测；兜底必须是“可读中文”，不能是原值 |
| T-05 | 技能/岗位“在名册里”，但关联资产没到场 | 引用了包外资产但种子只装了包内资产 | 矩阵 B 层：声明的技能必须**注册 + 安装 + 快照**三态一致 |
| T-06 | 数据看起来对，口径却漂移（61/68/70 各说各话） | 数量写死在文档/注释里 | 数量一律从可执行事实源派生；文档引用“派生结果”而非绝对值 |
| T-07 | 套件自己把自己跑挂（几轮后成片失败） | 夹具占用并发位/配额且不清理 | 跑前环境体检 + 跑后夹具排空；配额类拒绝要区分“系统保护”与“真失败” |
| T-08 | 验收环境被验收者污染（测试线程/标题出现在演示视图） | 套件与演示共用工作区 | 独立工作区/独立库；共用时披露残留并给修复建议 |
| T-09 | 事件字段“缺”与“未核实”无法区分 | 用省略字段表达“未核实” | 字段必须在位：无回执写 `synced:false`，并在 UI/报告同口径呈现 |
| T-10 | 平台组件写的事件在行业合规检查里被判违规 | 行业检查把平台对象/身份当行业对象 | 行业检查显式列出系统对象/身份白名单，并随平台组件演进同步维护 |
| T-11 | 浮层默认形态压住主工作区 | 默认尺寸按视口判断，而不是按**内容区**宽度 | 响应式断点用“内容区可用宽度”判定；默认最小打扰形态 |
| T-12 | 决策/审批界面把内部动作码当标题 | 服务端在缺标题时回落成动作码 | 客户端展示层必须做“技术串→中文”回收；服务端回落值不作为最终文案 |
| T-13 | 事件域/命名空间跨包重复，归属不清 | 组合装载后没有全局唯一性约束（只有包内约束） | 组合层做跨包唯一性对账（键、事件域、对象命名），冲突列警告并要求产品裁决 |
| T-14 | 验收结论“看起来很强”，复跑却复现不了 | 没冻结版本/数据/命令 | 报告写清 SHA、种子版本、命令、时间窗；产物与命令一一对应 |
| T-15 | 关键动作的耗时/点击数超标但没人发现 | 只做“存在性”检查 | 关键任务计时/计数，阈值写在 profile 并纳入通过线 |

## 13. 舰队落地机制

### 13.1 什么放在基座、什么放在本仓

| 资产 | 位置 | 分发方式 | 谁能改 |
|---|---|---|---|
| 本规范、检查单、报告模板 | 基座 `docs/`、`docs/acceptance/` | `sync/base-scope.json#requiredRootAssets`（整文件校验 + 分发） | 基座维护者（舰队提案） |
| 执行器（矩阵/UI/走查/报告渲染） | 基座 `scripts/acceptance/**` | base-sync `include: scripts/**` | 基座维护者 |
| 本仓 profile（角色/旅程/阈值/路由/启动命令） | **各仓** `acceptance/profile.json` | 不回流、不下发 | 本仓负责人 |
| 每轮产物 | 各仓 `outputs/acceptance/**`（或在会话工作区） | 不进基线（可归档） | 验收执行者 |

### 13.2 落地路径（三步）

1. 基座：规范 + 检查单 + 执行器 + 分发白名单（本次变更）；
2. 各仓：`acceptance/profile.json`（行业语义）+ 把 `pnpm acceptance:*` 接入 `.cnb.yml` 的**非阻断** stage（先观察，再逐步转成阻断）；
3. 每轮验收：按 §7 SOP 执行 → 产出 §5.1 五类证据 → 修 P0/P1 → 报告 + 陷阱清单回写。

### 13.3 与门禁的关系

- 真机验收是**发布前的人工/半自动关卡**，不替代 CI 门禁；两者互补：CI 管“每次提交”，验收管“每次发布/每个里程碑”。
- 建议节奏：新仓接入一次全量验收；此后每个发布里程碑（或每 2 周）跑一轮 L0–L5；L6/L7 每季度演练一次。
- 验收产物可作为发布证据附在 PR/Release 上（“无回执不算完成”的延伸）。

### 13.4 已知差异与兜底（首轮实测）

| 差异 | 现象 | 兜底 |
|---|---|---|
| 组合 API 只在获客仓 | 只有 `workloom` / `WorkLoom-growth` 有 `composeWorkforce` / `loadComposedAssets`；基座与其他行业仓只有单包装配 | 执行器先探测组合 API，缺失时按 `bundle.json` 依赖顺序做**本地组合**（同名取 `presetOwners`，围栏取并集）；报告里标注 `compositionSource=local-fallback`，该层证据等级降为 B |
| 来源包留痕字段 | `meta.sourceBundleId` / `shadowedBundleIds` 由组合装配器写入；单包仓没有 | 单包仓缺这两个字段判为「非缺陷」；组合仓缺则判失败 |
| B 端移动存储键 | 键名含 `productId`（`workloom:<productId>:b-mobile:access-token`） | 默认按本仓 `product.manifest.json` 推导；跨仓/跨实例冒烟可用 `profile.storage.bMobileTokenKey` 覆盖 |
| 演示库内容随仓不同 | 例如基座本地库当前种的是 hotel 演示工作区，而不是 `product.manifest.defaultBundle=ai-pm` | `primaryBundle` 未声明时按**工作区实际 `bundle_id`** 组合（并写警告），避免“拿错口径把正常态判成全红” |
| Playwright 装法不一 | 有的仓只有 `@playwright/test`，有的用 pnpm 隔离布局 | 执行器三路解析；确实没装则**明确报错**（禁止静默跳过 L3/L4） |
